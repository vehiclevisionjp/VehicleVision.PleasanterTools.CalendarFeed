**本アプリ（CalendarFeed）の導入・日常運用・更新・困ったときの手順。**
設計は [`アーキテクチャ方針.md`](アーキテクチャ方針.md)、実機で確かめた Pleasanter の挙動は [`実機検証結果.md`](実機検証結果.md)。
設定の一覧は [`App_Data/Parameters/README.md`](../src/VehicleVision.PleasanterTools.CalendarFeed.Web/App_Data/Parameters/README.md)。

> 書いてあるのは、ソース・テスト・実機（Pleasanter 1.5.8.1 ＋ 4 種の RDBMS ＋ 起動したアプリ）で確かめたことだけ。
> **確かめていないことは「未確認」と書いてある。**

## 2. 導入の前に決めること・用意するもの

| 項目 | 内容 |
| --- | --- |
| Pleasanter の API キー | **フィードごとに 1 本。** 見える範囲は、そのキーの利用者の権限で決まる（3 章） |
| API キー利用者のタイムゾーン | **運用の標準タイムゾーン（日本なら `Tokyo Standard Time`）にしておく。** `UTC` のままだと日付だけのレコードが 0:00 に読めず、終日の自動判定が効かない（[実機検証結果 1 章](実機検証結果.md)）。**運用開始後に変えない** |
| 本アプリの公開 URL | `CALENDARFEED_PUBLIC_BASEURL`。**HTTPS にする。** 管理者の cookie の `Secure` の判定にも使う（7 章） |
| RDBMS | Pleasanter が使うものに合わせる。**本番に SQLite は使わない** |
| 秘密の鍵 | `CALENDARFEED_SECRET_KEY`。**デプロイ先の秘密の保管先（環境変数）へ置く。** 失うと保管した API キーと管理者の 2 要素の共有鍵を復号できない（8 章） |
| サーバの時計 | **NTP で合わせる。** TOTP は前後 30 秒までのずれしか許さない |

## 3. Pleasanter 側の準備

1. **フィード用の利用者を作り、API キーを発行する。** `Users.TimeZone` を運用の標準タイムゾーンにする。
2. **その利用者に、フィードに出すサイトの読み取り権限を与える。** 見せたくないサイトは権限を与えない（これがフィード間の分離になる）。
3. **件名・場所・説明で選択肢・リンク・ユーザーの列を使うなら、リンク先サイトの読み取り権限も要る。**
   解決は API キーの利用者の権限の範囲でしか効かない（ソース上の根拠。リンク列の解決は**未確認**）。
4. 項目拡張（`Date001` 以降など）を使うなら、Pleasanter 側で拡張を有効にしておく。
   `trial` の CodeDefiner は既定で `Class` しか拡張しない（[実機検証結果 6 章](実機検証結果.md)）。
5. 数値の小数桁は Pleasanter の列の設定で決まる（既定 0。保存時に丸められる）。小数を出すなら、Pleasanter 側で桁を増やす。

> **Pleasanter の API 回数制限**を超えないよう、生成した `.ics` は 300 秒キャッシュする（`Feed.json` の `CacheSeconds`）。
> 制限を超えたときの挙動は**未確認**。

## 4. 導入

### 4.1 DB を作る

| RDBMS | 手順 |
| --- | --- |
| SQLite | 何もしない（`App_Data/calendarfeed.db`。簡易用） |
| SQL Server | **データベースを先に作る**（マイグレーションは作らない）。接続文字列の `Encrypt=False` は無視して暗号化する。証明書の確認を緩めるなら `TrustServerCertificate=True` |
| PostgreSQL | データベースを作る |
| MySQL | **`utf8mb4` のデータベースを作る**（`CREATE DATABASE calendarfeed CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_as_cs;`）。表はマイグレーションが `utf8mb4` へ直す |

### 4.2 設定する

秘密の値は**環境変数**で与える（`App_Data/Parameters/*.json` へ実値を書かない。`*.local.json` はローカル開発用）。

```bash
export CALENDARFEED_PUBLIC_BASEURL=https://calendar.example.com
export CALENDARFEED_PLEASANTER_BASEURL=https://pleasanter.example.com
export CALENDARFEED_PLEASANTER_TIMEZONE=Asia/Tokyo         # 既定のタイムゾーン（フィードごとに上書きできる）
export CALENDARFEED_DB_PROVIDER=PostgreSql                 # Sqlite / SqlServer / PostgreSql / MySql
export CALENDARFEED_DB_CONNECTIONSTRING='Host=…;Database=calendarfeed;Username=…;Password=…'

# 秘密の鍵（フィードごとの API キーと管理者の TOTP の共有鍵を暗号化する）。1 度だけ作って保管する
dotnet run --project src/VehicleVision.PleasanterTools.CalendarFeed.Web -- --generate-secret-key
export CALENDARFEED_SECRET_KEY=<出力された値>
```

- 設定ファイルの置き場と見つかったファイルは、**起動時にログへ出る**（1 つも無ければ警告）。
- `CALENDARFEED_ADMIN_TWOFACTOR` は `required` / `optional`（既定）/ `disabled`。**知らない値は起動時に落ちる。**
  導入時は `required` を勧める（登録するまでログインが完了しない）。

### 4.3 起動する

**先に管理画面（Svelte）を組み立てる。** 成果物は `.Web` の `wwwroot/admin` へ出て、`dotnet publish` に含まれる（Node.js 24 が要る。配布先には要らない）。
組み立てていないと `/admin/` は 404（`The admin UI is not built`）になり、API だけが動く。

```bash
(cd src/VehicleVision.PleasanterTools.CalendarFeed.Frontend && npm ci && npm run build)
dotnet publish src/VehicleVision.PleasanterTools.CalendarFeed.Web -c Release -o publish
ASPNETCORE_URLS=http://localhost:5000 dotnet publish/VehicleVision.PleasanterTools.CalendarFeed.Web.dll
```

管理画面は `{公開 URL}/admin/` を開く（画面の写しは [`管理画面-画面の写し一覧.md`](管理画面-画面の写し一覧.md)）。
画面は **CSP（自分のオリジンだけ・インライン不可）** で配信され、API の応答は `no-store`。

> 配布用の成果物のうち、**コンテナイメージを作る `Dockerfile` は用意した**（`docker build -t calendarfeed .`。ACR への発行は `aks-image.yml`）。
> 管理画面のビルドもイメージの中で行う。非 root（`$APP_UID`）で 8080 番を待ち受ける。**設定・秘密は環境変数で渡す**（イメージへ実値を入れない）。
> 手元で Pleasanter の検証環境ごと動かすなら `compose.yaml`（先頭のコメント参照）。ZIP 配布と `dotnet publish` は従来どおり。
> サブパス配置（`/calendarfeed/` など）は**未対応**
> AKS へ入れるときは [`AKS-導入更新運用手順書.md`](AKS-導入更新運用手順書.md)（Helm チャート `deploy/aks/calendarfeed/`）
> （管理者の cookie の `Path` が `/admin` 固定のため）。

- **マイグレーションは起動時に自動で当たる。** 無効にするなら `CALENDARFEED_DB_AUTOMIGRATE=false`（その場合は手で当てる必要がある）。
- プロキシを通す前に、**ローカルで次の 4.4 まで済ませる**（空の状態を公開しない）。

### 4.4 最初の管理者を作る

**管理者が 1 人も居ないときだけ**作れる。**公開する前に作る**（空の状態を放置すると、最初に来た人が管理者になる）。

```bash
B=http://localhost:5000
curl -c jar -X POST $B/admin/api/setup -H "Content-Type: application/json" \
  -d '{"loginId":"admin","password":"<12 文字以上のパスワード>"}'   # 201。2 回目は 409
```

- パスワードの条件は `Security.json`（最低 12 文字。ログイン ID と同じは不可。`PasswordPolicies` で正規表現の条件を足せる。先読み・後方参照・原子グループは使えず、起動時に落ちる）。
- **作った後はすぐログインして 2 要素を登録する**（4.5）。

### 4.5 ログインして 2 要素を登録する

```bash
curl -b jar -c jar -X POST $B/admin/api/login -H "Content-Type: application/json" \
  -d '{"loginId":"admin","password":"<パスワード>"}'
# → {"step":"enroll"}（required）または {"step":"done"}（optional で未登録）

curl -b jar -c jar -X POST $B/admin/api/me/totp/begin        # {"secret":"…","uri":"otpauth://…"}
# 認証アプリ（Google Authenticator など）へ uri か secret を登録し、表示された 6 桁を送る
curl -b jar -c jar -X POST $B/admin/api/me/totp/complete -H "Content-Type: application/json" \
  -d '{"code":"123456"}'                                     # {"recoveryCodes":[…10 本…]}
```

- **復旧コード 10 本はこのとき 1 度だけ表示される。** 紙か秘密の保管先へ。**使い切り。** 端末を失ったときの唯一の入口（8 章）。
- 登録し直すと、前の復旧コードは消える。

### 4.6 フィードを作る

```bash
curl -b jar -X POST $B/admin/api/feeds -H "Content-Type: application/json" \
  -d '{"name":"共有予定","siteId":123,"apiKey":"<Pleasanter の API キー>","apiKeyUserTimeZoneId":"Asia/Tokyo","language":"ja"}'
# → {"feed":{…,"hasApiKey":true,"apiKeyHint":"e1f6"},"url":"https://…/feeds/<トークン>.ics"}
```

- **応答の `url`（購読 URL）はこのとき 1 度だけ得られる。** トークンは DB に SHA-256 しか置かないので、後から取り出せない（失くしたら再発行）。
- **API キーは登録後は返さない**（`hasApiKey` と末尾 4 文字だけ）。
- 列の対応・書式・テンプレートの書き方は [`アーキテクチャ方針.md`](アーキテクチャ方針.md) 4 章。

| `mapping` の例 | 意味 |
| --- | --- |
| 指定なし | 件名は Pleasanter が組み立てたタイトル（`ItemTitle`）、開始 `StartTime`、終了 `CompletionTime`、説明 `Body` |
| `{"startColumn":"DateA","endColumn":"Date001"}` | 開始・終了に日付の列 |
| `{"summaryTemplate":"{ClassA}：{Title}（{DateB:yyyy/MM/dd}）"}` | 件名を列の組み合わせで作る。**日付・数値には書式が必須** |
| `{"startColumn":"DescriptionA","startFormat":"yyyy/MM/dd HH:mm"}` | 文字の列に入った日付を書式で読む。**書式に合うレコードだけが出る**（形式を揃えて入力する） |
| `"allDay":"Never"` / `"Always"` | 終日の判定（既定 `Auto`＝開始が 0:00 で終了が無いか 0:00 なら終日） |

### 4.7 カレンダーへ登録する

購読 URL を、各カレンダーの「URL から購読」（インターネットカレンダー）へ貼る。

- 本アプリは `REFRESH-INTERVAL` と `X-PUBLISHED-TTL`（既定 5 分）を返し、`ETag` に対応する。**更新の間隔はクライアントが決める**。
  各クライアントがどの間隔で取りに来るかは**未確認**。
- 購読 URL は**パスワードと同じ扱い**（知っていれば誰でも読める）。共有するときは相手を限る。

## 5. 日常運用

| やること | 方法 | 備考 |
| --- | --- | --- |
| Pleasanter の API キーを差し替える | `PUT /admin/api/feeds/{id}/apikey` `{"apiKey":"…","apiKeyUserTimeZoneId":"…"}` | 生成済みの `.ics` のキャッシュは捨てられる。**タイムゾーンを変えると全予定の時刻がずれる**ので、API キー利用者の変更時以外は変えない |
| 購読 URL が漏れた | `POST /admin/api/feeds/{id}/rotate` | **旧 URL はその場で使えなくなる。** 新しい URL を購読者へ配り直す |
| フィードを止める | `DELETE /admin/api/feeds/{id}` | 以後 404 |
| フィード・API キーの確認 | `GET /admin/api/feeds/` | トークンも API キーも出ない |
| 自分のパスワードを変える | `POST /admin/api/me/password` | **他の端末のセッションが失効する** |
| 管理者のログアウト | `POST /admin/api/logout` | サーバ側のセッションがその場で失効する |

### アプリケーション設定（管理画面から編集する）

**Questionnaire の「アプリケーション設定」に則る。** メール・Pleasanter の接続先・フィードの取得・2 要素の方針・パスワードの最低の長さ・監査ログの保存日数などは、DB に保管し、管理画面から編集する
（`GET /admin/api/settings/` で一覧、`PUT /admin/api/settings/` `{"values":{"CALENDARFEED_FEED_CACHESECONDS":"60"}}` で保存。**権限 `settings.manage`＝Administrator のみ**）。

- **優先順位は 外部設定（環境変数・`App_Data/Parameters`）＞ DB ＞ 既定値。** 外部設定に値があるものは**固定**で、画面からは変えられない（`isFixed`）。
  **画面から編集させたい設定は、環境変数・Parameters に書かない**（同梱のファイルは値を `null` にしてある）。
- **保存したらその台へすぐ反映され、他の台へは 30 秒以内**（再起動は要らない）。1 つでも不正な値があれば、何も保存しない。値が `null` なら既定へ戻す。
- **秘密（SMTP パスワード・Pleasanter の共通 API キー）は暗号化して保管し、画面へは返さない。** 空なら変えない。⚠️ **秘密の鍵（`CALENDARFEED_SECRET_KEY`）を失うと復号できない**: 起動は止まらず、その設定は空として扱われる（`unreadable`）ので、画面で再入力する。
- **メールを有効にするには、差出人・公開 URL・送信経路に応じた設定（SMTP サーバー・SES のリージョン・ACS のエンドポイント）が要る**（足りなければ断る）。`POST /admin/api/settings/mail/test` で、**自分のログイン ID（メールアドレス）宛て**に試し送信できる。
- **Pleasanter の URL が未設定でもアプリは起動する。** 設定するまで、フィードを取りに行くと分かるメッセージで失敗する（`GET /admin/api/feeds/` の最後の取得結果／ログ）。
- 変えた設定の**名前だけ**を監査ログへ残す（値・秘密は残さない）。
- **画面から編集しない設定**（DB 接続・秘密の鍵・転送ヘッダの信頼ネットワーク・パスワード条件の正規表現・メール送信ワーカーの切り替え）は、ファイル／環境変数のまま
  （[`App_Data/Parameters/README.md`](../src/VehicleVision.PleasanterTools.CalendarFeed.Web/App_Data/Parameters/README.md)）。

### フィードの編集

`PUT /admin/api/feeds/{id}`（権限 `feeds.write`）で、名前・サイト ID・列の対応・絞り込み・言語・API キー利用者のタイムゾーンを**置き換える**。**購読 URL（トークン）と API キーは変わらない**（API キーは `PUT …/apikey`）。
生成済みの `.ics` のキャッシュは捨てられる。変えた項目の名前だけを監査ログへ残す。

**表示する期間（Issue #67）。** フィードごとに、**今日を基準に過去・未来を何日までとるか**を決める（`PastDays`・`FutureDays`。0〜36500 日。**空（`null`）は無制限＝開区間**）。
**新しいフィードの既定は「過去 365 日・未来は無制限」**（既存のフィードも、このリリースで同じ値になる。1 年より前の予定は購読中のカレンダーから消えるので、残したいフィードは画面から「無制限」にする）。

- **期間と重なる予定を出す。** 開始が期間の終わりより前で、終了が期間の始まりより後なら出す（**期間の前に始まって今も続く長い予定は消えない**）。終了の無い予定は、開始が期間の中にあれば出す
- **日の単位。** 過去 `N` 日は「今日の 0 時の `N` 日前から」、未来 `M` 日は「今日から `M` 日後の日の終わりまで」。今日は **API キー利用者のタイムゾーン**の今日
- **Pleasanter への絞り込みは粗いもの**（日付の列だけ。取り過ぎない）で、**正確な判定は取得した後**に本アプリが行う。日付が文字の列（`Class*` など）に入っているときは、Pleasanter では絞れないので、取得した後の判定だけが効く（この場合、全件を取ってから外すので、件数の上限（`CALENDARFEED_FEED_MAXEVENTS`）に注意）
- 利用者が同じ列に書いた絞り込み（`Filters`）は、上書きしない
- **件数の上限との関係:** 期間を絞ると、取得する件数が減り、上限（既定 5000 件）に当たりにくくなる。両側を無制限にした大きなサイトでは、上限で古い順に切れる恐れがある

### Pleasanter の API の回数の上限

Pleasanter は、**サイトごと・1 日ごと**に API の回数を制限できる（`Api.json` の `LimitPerSite`。0 は無制限。契約の設定があればそちらが優先）。**Get も Create も数える。**
超えると Pleasanter は HTTP 429 を返し、**API キーの利用者のタイムゾーンの日付が変わるまで戻らない**（実機検証結果 13 章）。

- **本アプリの挙動:** 429 は専用の失敗（`RateLimited`）。購読 URL は `503`＋`Retry-After`（日付が変わるまでの秒数。最短 60 秒・最長 24 時間）を返し、購読側のカレンダーは手元の予定を残す。
  管理画面の「最後の取得結果」に「Pleasanter の API の回数の上限に達しました」と出る。取得の失敗の通知（上の節）を有効にしていれば、連続して失敗したとき、**対処つきでメールが届く**
- **使う回数の見積もり:** キャッシュが切れるたびに、ページごとに `Get` を 1 回（表示名の解決が要る列があるときは 2 回）呼ぶ。購読者が絶えず取りに来る場合、**1 フィードあたり 1 日に最大 `86400 ÷ キャッシュ秒数 × 1〜2` 回**
  （既定の 300 秒で 288〜576 回）。**同じサイトを使う複数のフィードの分は足される**（上限はサイトごと）
- **対処:** ①Pleasanter 側の上限を上げる ②**キャッシュ秒数を伸ばして**（`CALENDARFEED_FEED_CACHESECONDS`）取りに行く回数を減らす ③フィードの絞り込み・期間を狭めて 1 回あたりの件数（ページ数）を減らす

### 取得の失敗の通知（任意）

フィードの取得（Pleasanter への問い合わせ）が失敗しても、購読側のカレンダーは古い予定を見せ続けるだけで、誰も気づかない。
**連続の失敗が閾値に届いたら、フィードを編集できる管理者へメールで知らせる**（Issue #48）。**既定は無効**（メール送信を有効にしたうえで、設定の「フィードの取得の失敗が続いたらメールで知らせる」を有効にする）。

- **閾値**（既定 3 回）に届いたとき 1 通、**回復したとき 1 通**。続く間は、**再通知の間隔**（既定 24 時間）が過ぎるまで知らせない。一時的な 1 回の失敗では知らせない
- 宛先は、**有効で、フィードを編集する権限（`feeds.write`）を持つ管理者のうち、ログイン ID がメールアドレスの人**。言語は各自の言語。宛先が 1 人もいなければ、ログへ警告だけを残す
- 本文には、フィードの名前・連続の回数・最後の時刻・対処の案内・管理画面の URL（公開 URL から作る）だけを載せる。**フィードの URL（トークン）・API キー・Pleasanter の応答の文面は載せない**
- 通知するかどうかは DB の 1 文の UPDATE で決めるので、**複数台で同時に失敗しても通知は 1 回**。送るのはアウトボックス経由（送信ワーカーが送る）
- フィードの一覧の「最後の取得結果」に、連続の失敗が 2 回以上のとき「連続 N 回失敗」が出る
- 通知は、**フィードが取得されたとき**に判断する（誰も購読していないフィードは、失敗に気づけない）

### 管理者の管理

方式は **Questionnaire の「管理者の管理」に則る**。Pleasanter のユーザーとは連動しない（認可は本アプリの役割だけで行う）。

**権限の集合を役割に割り当てる。** 画面は `GET /admin/api/me/` の `permissions` で出し分ける。権限は cookie に焼かず、要求のたびに役割から引く（役割を変えたら、その場で効く）。
知らない役割には何も持たせない。

| 役割 | 権限 | 用途 |
| --- | --- | --- |
| `Administrator`（特権管理者） | すべて | |
| `FeedAdministrator`（フィード管理者） | `feeds.read` `feeds.write` `feeds.delete` `outbox.read` | フィードの運用を任せる相手。**人には触れない** |
| `UserAdministrator`（ユーザ管理者） | `users.read` `users.write` `users.resetTwoFactor` `audit.read` | 人の出入りと、その記録。**フィードには触れない** |
| `Editor`（フィード編集者） | `feeds.read` `feeds.write` | 作るところまで。**失効はできない** |
| `Auditor`（監査担当） | `audit.read` `outbox.read` | 見るだけ |

権限の内訳: `feeds.read`＝一覧、`feeds.write`＝作成・トークン再発行・API キーの登録、`feeds.delete`＝失効、`outbox.read`＝メールの送信状況、
`audit.read`＝監査ログ、`users.read`＝管理者の一覧、`users.write`＝追加・招待・役割・停止・端末の失効、`users.resetTwoFactor`＝他人の 2 要素の解除。

| やること | 方法 | 権限 | 備考 |
| --- | --- | --- | --- |
| 管理者の一覧（最終ログイン・棚卸し） | `GET /admin/api/users/`（`?staleOnly=true` で絞る） | `users.read` | `invitationPending`＝招待中（未使用で期限内）。`stale` は **90 日以上ログインしていない**人（招待中・無効は対象外。一度もログインしていなければ作成日から数える） |

| 招待を出し直す | `POST /admin/api/users/{id}/invitation` | `users.write` | **前の招待は使えなくなる。** 受け取り済みの人にも出せる（**パスワードの決め直しになり、受け取ると以前のパスワードで張られたセッションはすべて失効する**）。無効化されている人には出せない |

| 他の人の端末を失効させる | `DELETE /admin/api/users/{id}/sessions` | `users.write` | |

- **招待を受け取る人**（認証なし）は、招待の URL（`{公開 URL}/admin/invitations/accept?token=…`）の画面から
  `POST /admin/api/invitations/accept` `{"token":"…","password":"…"}` で**パスワードを自分で決める**。
  パスワードの条件は最初の管理者・パスワード変更と同じ（**条件を満たさない値は、招待を使い切る前に断る**）。受け取ると、**2 要素の方針
  （`CALENDARFEED_ADMIN_TWOFACTOR`）に従って**応答の `next` が決まる: 登録済みなら `totp`（まず 2 要素）、必須で未登録なら `enroll`（その場で登録）、それ以外は `done`（そのまま入れる）。
  この URL を開く画面は、管理画面の「招待の受け取り」（`/admin/invitations/accept`）。
- **使えない招待は理由を問わず同じ 404**（期限切れ・受け取り済み・出し直しで無効・取り消された・止められた・形が違う）。総当たりはログインと同じレート制限の枠で遅くする。
- **トークンは SHA-256 だけ保管する**（`AdminInvitations`）。PBKDF2 は使わない（256 ビットの乱数なので辞書攻撃の的にならず、PBKDF2 だと全件を総当たりで照合することになり、認証前の入口を重い計算に晒す）。
- **最後の有効な Administrator は、無効化も降格もできない**（締め出しを防ぐ。**止まっている人も、一度もログインしていない人も数えない**）。
  判定は 1 文の UPDATE の中で行い、同時の変更は Administrator の行をロックして 1 つずつにする
  （PostgreSQL では、1 文の UPDATE だけだと 2 人が同時に互いを外したとき両方通ってしまうことを実機で確認した）。**自分自身の無効化・役割の変更は断る**（操作ミスで自分を外さない）。

#### 招待メール

- **本人へ直接送る**（手渡しの途中で漏れる経路を減らす）。送れない構成（メールを有効にしていない・ログイン ID がメールアドレスでない・`CALENDARFEED_PUBLIC_BASEURL` が無い）でも
  **招待は出せる**: 応答の `invitation.url` を手で渡す。`mailSent` が `false` なら、手で渡す必要がある。
- **メールは既定で無効。** 設定は**管理画面から編集する**（上の「アプリケーション設定」。`Mail.json` / `CALENDARFEED_MAIL_*` に書くと固定になる）。
  送信経路は **SMTP**（587 番の認証付きリレー。SendGrid・Amazon SES・Microsoft 365 など）、**Amazon SES**（HTTPS。IAM ロールで通る）、**Azure Communication Services**（HTTPS。マネージド ID で通る）。
  SES・ACS は**資格情報の設定口を作っていない**（秘密を保管しないため）。**SMTP のパスワードは環境変数か `Mail.local.json` で与え、画面にも返さない。**
- **リンクは `CALENDARFEED_PUBLIC_BASEURL` から作る。要求の Host から組み立てない**（host header injection）。
- **送信待ち（`MailOutbox`）には、宛先・件名・本文を 1 つにまとめて暗号化して置く**（`CALENDARFEED_SECRET_KEY`）。平文の列は無く、**送れたら行ごと消える**。
  **招待の URL はそれだけで管理者になれる値**なので、送信待ちの識別子にもトークンを使わない。
  ⚠️ **秘密の鍵を失うと、送信待ちの行は復号できずデッドレターへ回る**（2 要素の共有鍵と同じ前提）。招待を出し直す。
- **送信はアプリの中のワーカーが行う**（送るものが無いときは 10 秒おきに見る）。一時的な失敗（4xx）は指数的に間隔を伸ばして再送し（30 秒から最大 1 時間、10 回まで）、
  恒久的な失敗（5xx）・上限超え・復号できない行は**デッドレターへ分離する**（黙って溜め続けない。ログと `GET /admin/api/mail/status` の件数で気付く）。
  送信数は 1 分あたり 60 通までに抑える（`CALENDARFEED_MAIL_SEND_PER_MINUTE`）。
- **複数台にするとき**: 確保は 1 文の UPDATE で原子的なので、全台でワーカーを動かしても**二重には送らない**（実機で確認）。送信を担う台を絞りたいときは、他の台で `CALENDARFEED_MAIL_WORKER=false`。
- 動作確認は Mailpit（SMTP 1025・画面 8025）が使える。

- 追加・出し直し・受け取り・無効化・有効化・役割・2 要素の解除・端末の失効は、すべて監査ログに残る。
- **管理者の操作・ログインの履歴（監査ログ）は DB の `AuditLogs` に残る。** ログイン・ログアウト・失敗・締め出し・復旧コードの使用、
  パスワード変更、2 要素の登録・解除、フィードの作成・トークン再発行・API キーの差し替え・失効。
    - **失敗も残す。** ログイン失敗には理由（`unknown-user` / `bad-password` / `disabled` / `locked`）が `Detail` に入る（外への応答は同じ）。
    - **パスワード・API キー・トークン・復旧コード・TOTP の数字は残さない。** 利用者が打ち込んだ**ログイン ID は、居ない ID でも残る**
      （総当たりの追跡のため）。ログイン ID の欄へパスワードを打ち間違えた場合は、それが残り得る点に注意する。
    - 読むのは `GET /admin/api/audit-logs/`（ログイン済みの管理者のみ。新しい順。`limit`・`before`（前のページの最後の `occurredAt`）・
      `admin`・`action`・`failed=true` で絞る）。管理画面では「監査ログ」で絞り込んで読める（操作・失敗だけ。失敗の理由は画面の言語で補足される）。
    - **残す日数は `CALENDARFEED_AUDITLOG_RETENTION_DAYS`（既定 365。`0` なら消さない）。** 6 時間ごとに古い記録を消す。
      法令・社内規程で期間が決まっているなら合わせる。消さない設定にすると、表は増え続ける。

### SAML 2.0 でのログイン（任意）

**既定は無効。** 有効にすると、ログイン画面に SAML のボタンが出る（パスワードでのログインも使える）。
**IdP が証明するのは「誰か」だけで、認可は本アプリの役割で行う。** 設定は管理画面の「SAML ログイン」の群から編集する
（`CALENDARFEED_SAML_*`。DB へ保管。環境変数で固定もできる）。

1. 管理画面の設定で、IdP へ登録する 2 つの URL（SP のメタデータ・ACS）を確かめる。**公開 URL（`CALENDARFEED_PUBLIC_BASEURL`）を先に設定する**
2. IdP（Microsoft Entra ID・Keycloak など）へ登録する。SP のエンティティ ID は、IdP へ登録した値と同じにする（メタデータ URL にするのが一般的）
3. 本アプリへ、IdP のエンティティ ID・シングルサインオン URL・署名証明書（PEM）を設定して有効にする
4. **本アプリに居ない利用者の扱い**: `Reject`（既定。招待された人だけ通す）／`Register`（自動で作る。役割は `REGISTERROLE`）

- **HTTPS と秘密の鍵が要る。** ログインの途中で使う cookie が `SameSite=None; Secure` のため。鍵が無いと開始が 503 になる
- **ログイン ID** は NameID（既定）か属性（`LOGINIDCLAIM`）から取る。本アプリの管理者の ID と一致した人が入る
- **2 要素は飛ばさない。** SAML で入っても、本アプリの 2 要素の設定（`TWO_FACTOR`）に従う
- **失敗は監査ログへ残す**（`login.saml_failed`。`Detail` に理由。画面へは「登録されていない／無効／完了できない」の 3 種類だけ出す）。自動登録は `user.saml_registered`
- **単一ログアウト**: 画面のログアウトは、IdP の単一ログアウト URL を設定していれば IdP へも頼む。IdP 側から来たログアウトは `/admin/api/saml/slo` が受け、該当するセッションを捨てる
- **宛先（Destination）は本アプリが確かめる**（ライブラリは見ないため）。署名・宛先・要求への応答（InResponseTo）・有効期間のどれかが外れたら通さない
- 検証用の IdP は [`tools/saml-idp`](../tools/saml-idp/README.md)（Keycloak）

### Pleasanter のログインでの管理画面（任意）

**既定は無効。** Pleasanter にログイン済みのブラウザから、そのまま管理画面へ入れる（シングルサインオン）。
**認可は本アプリの役割で行い、Pleasanter が証明するのは「誰か」だけ。** 設定は管理画面の「Pleasanter のログイン」の群
（`CALENDARFEED_PLEASANTERSSO_*`。DB へ保管。環境変数で固定もできる）から編集する。

**仕組み。** ログイン画面の釦が `POST /admin/api/pleasanter-sso/check` を呼ぶ。サーバはブラウザから届いた Pleasanter の cookie を
Pleasanter の標準 API（`POST /api/users/get` を利用者 ID `Own` で絞る）へ転送して本人を確かめ、ログイン ID（Pleasanter の `LoginId`）で
本アプリの管理者へ結び付けて、本アプリの cookie を発行する。読むだけで、Pleasanter には何も書かない。
まだ Pleasanter にログインしていなければ、画面が Pleasanter のログイン画面を別のウィンドウで開き、済むまで確かめ続ける。

⚠️ **本アプリと Pleasanter は、同じホスト名で動かすこと**（パスだけ分ける。例: `https://example.com/` が Pleasanter、`https://example.com/calendarfeed/` が本アプリ）。
cookie はホスト単位でしか届かないので、別のホスト名では使えない。ポートは区別されない。

1. 本アプリから Pleasanter へ届く URL（**内部 URL**。サーバ間。ブラウザへは渡さない）と、ブラウザで開く Pleasanter の**ログイン画面の URL**（`/` で始まる同じホストのパスでよい）を設定する
2. 「接続を試す」で確かめる（同じブラウザで Pleasanter にログインし、設定を保存してから）。本人が返れば、本アプリの管理者として登録済みかも出る
3. 有効にする

- **本アプリに居ない利用者**は、既定では通さない（`Reject`）。`Register` にすると自動で作る（役割は `REGISTERROLE`。**`Administrator` にすると、許可した所属の全員が全権を持つ**）。
  **自動登録は、許可する組織（`ALLOWEDDEPTIDS`）かグループ（`ALLOWEDGROUPIDS`。子グループも含む）を決めたときだけ。** 未設定のままでは、Pleasanter の全利用者が入れてしまうので作らない
- **2 要素は飛ばさない。** 本アプリで 2 要素を登録済みなら、Pleasanter から来ても数字を求める。必須の方針なら登録させる。Pleasanter 側の 2 要素は、終えるまで Pleasanter が認証 cookie を出さないので、ここへ来る時点で済んでいる
- **確かめ直す。** 一定間隔（既定 5 分）で Pleasanter へ確かめ直し、**Pleasanter でログアウトした・別の人がログインし直した・所属が外れた・機能を無効にした・Pleasanter へ問い合わせられなかった**ときは、本アプリからも落とす（問い合わせられないときにセッションを延ばさない）。最後に確かめた時刻はセッションの行に持つので、複数台でも揃う
- **利用者の API 利用が禁止されている**（Pleasanter が 403 を返す）ときは、本アプリの Pleasanter 接続設定（URL と共通の API キー）で利用者を引き直す。**cookie を転送する問い合わせに API キーは載せず、API キーを使う問い合わせに cookie は載せない**（規約 8）
- **転送する cookie は名前で絞る**（既定は `.AspNetCore.Cookies` と `Pleasanter_SessionGuid`。前方一致）。**本アプリ自身の cookie（`calendarfeed_` で始まるもの）に当たる指定は保存できない**
- **ログアウト**: 本アプリのセッションを捨てた後、Pleasanter のログアウト画面の URL を設定していれば、そこへ進む（Pleasanter のログインが残っていると、すぐに入り直せてしまうため）
- 失敗は監査ログへ残す（`login.pleasanter_sso_failed`。`Detail` に理由）。自動登録は `user.pleasanter_sso_registered`。「まだログインしていない」だけの問い合わせは残さない
- 確認の入口は、画面が待つ間くり返し呼ぶので、パスワードのログインとは別のレート制限（IP ごと 5 分に 300 回）
- 最初の管理者は、Pleasanter から作らせない（誰でも全権を取れてしまう）

動作を確かめた Pleasanter は 1.5.8.1（2026-10-15）。検証手順は [`tools/pleasanter-testenv`](../tools/pleasanter-testenv/README.md)。

## 6. 更新とロールバック

```mermaid
flowchart TD
    A["DB のバックアップ"] --> B["アプリを止める"]
    B --> C["新しい版を配置"]
    C --> D["起動（マイグレーションが自動で当たる）"]
    D --> E{"確認 4 点"}
    E -->|"通った"| F["完了"]
    E -->|"通らない"| G["旧版を戻し、DB をバックアップから戻す"]
```

1. **DB のバックアップを取る。**
2. アプリを止め、新しい版を配置して起動する。**マイグレーションは起動時に自動で当たる。**
3. 確認する: ①起動ログに `DB:` が出てエラーが無い ②`GET /admin/api/status` が 200 ③管理者がログインできる ④購読 URL で `.ics` が取れる。
4. **ロールバック＝旧版のバイナリ ＋ バックアップから DB を戻す。** マイグレーションの `Down` は用意してあるが、**自動では実行しない**（実行は `MigrateUp` だけ）。
5. **複数インスタンスにするとき**: マイグレーションは、DB の排他ロックで 1 台だけが当てる（後から来た台は待つ。「複数台での運用」の章）。
   手で当てたいなら、全台を `CALENDARFEED_DB_AUTOMIGRATE=false` にして、先に 1 台で当てる。
   `.ics` のキャッシュはプロセスごと（共有しない）。管理者のセッションは DB なので共有される。

## 7. リバースプロキシ・HTTPS

- **TLS はプロキシで終端してよい。** 本アプリの cookie の `Secure` は、**要求が HTTPS か、`CALENDARFEED_PUBLIC_BASEURL` が `https://` のとき**に付く。
  プロキシ配下では要求が HTTP で届くので、**公開 URL を `https://` で設定する**（これを忘れると、cookie に `Secure` が付かない）。
- ⚠️ **プロキシの背後では、転送ヘッダを信頼するネットワークを設定しないと、レート制限が全員で 1 つの枠になる**。
  本アプリは既定では `X-Forwarded-For` を無視し、クライアントの IP としてプロキシの IP を見る。
    - 管理者のログイン: **5 分に 10 回**で全員が 429
    - 購読フィード: **1 分に 60 回**で全購読者が 429
- **`CALENDARFEED_FORWARDED_PROXY_NETWORKS`（`Security.json` の `ForwardedProxyNetworks`）にプロキシのネットワークを CIDR で書く**（カンマ区切り。例: `10.0.0.0/8,192.0.2.10/32`）。
    - **書いたネットワークから届いた要求の `X-Forwarded-For` / `-Proto` / `-Host` だけを信頼する。** それ以外の相手のヘッダは無視する（偽装してレート制限を逃れさせない）。
      ループバックも、書かなければ信頼しない。
    - 書き間違い（CIDR でない値）は**起動時に落ちる**。
    - 要求が HTTPS かの判定（cookie の `Secure`）も、`X-Forwarded-Proto` に従う。
    - **プロキシは、外から届いた `X-Forwarded-For` を引き継がず、自分が見た相手の IP で上書きするか追記する設定にする。**
      本アプリは連なった最後の 1 段だけを見る（`ForwardLimit` の既定 1）。プロキシが複数段のときは未確認。
- **購読 URL のトークンが、プロキシ・Web サーバのアクセスログに残る**（パスに `/feeds/<トークン>.ics` が入る）。
    - アプリのログには出さない（`Microsoft.AspNetCore.Hosting.Diagnostics` を Warning にしてある）。
    - プロキシのログは**アクセスできる人を限り、保管期間を短くする**。Nginx ならパスを伏せて記録する設定が書ける（下は**動作未確認の例**）。
      IIS・Azure のログでの伏せ方は**未確認**。

```text
# Nginx の例（動作未確認）。/feeds/<トークン>.ics を /feeds/[masked].ics として記録する
map $request_uri $masked_uri {
    ~^/feeds/[^/?]+\.ics$  /feeds/[masked].ics;
```

## 複数台での運用

**既定は 1 台。** 台数を増やしても動くように、状態は DB に置いてある。**外部の共有基盤（Redis など）は要らない。**
増やすときの前提と、台ごとに違う所は次のとおり（Issue #49。点検してテストで確かめた）。

**全台でそろえること**

- **秘密の鍵（`CALENDARFEED_SECRET_KEY`）は、全台で同じ値にする。** 設定の秘密・フィードの API キー・TOTP の共有鍵・メールの送信待ち・SAML のログインの途中の cookie が、この鍵で暗号化される（違う台では読めない）
- **公開 URL（`CALENDARFEED_PUBLIC_BASEURL`）も全台で同じ。** SAML の宛先・メールのリンク・cookie の `Secure` の判定に使う
- 信頼するプロキシの設定（`CALENDARFEED_FORWARDED_PROXY_NETWORKS`）で、ロードバランサ越しのクライアントの IP を見る。見ないと、全員がロードバランサの IP として数えられる
- **セッションの固定（スティッキー）は要らない。** セッション・招待・設定・監査ログは DB にある

**台をまたいで共有されるもの（DB）**

| 項目 | 動き |
| --- | --- |
| 管理者のセッション・2 要素の途中・Pleasanter のログインの再検証の時刻 | DB。どの台でも通る |
| ログインの試行・Pleasanter のログインの確認のレート制限 | **DB の数えを共有**（IP ごと。5 分に 10 回・300 回）。台数が増えても枠は増えない。**DB を読み書きできないときは、その台の中だけで数える**（止めない）。古い行は 1 時間ごとに消す |
| メールの送信 | 確保は 1 文の UPDATE で原子的。**全台で送信ワーカーを動かしても二重には送らない**。台を絞るなら、送信しない台を `CALENDARFEED_MAIL_WORKER=false` にする |
| フィードの取得の失敗の通知 | 通知するかは 1 文の UPDATE で決める。**複数台で同時に失敗しても 1 通** |
| マイグレーション | 起動時に、DB の排他ロックで 1 台だけが当てる。後から来た台は待つ（最大 5 分。超えたら起動に失敗する）。当て終わった後は何もしない |
| 設定 | 保存した台はすぐ、**他の台は 30 秒以内**に反映する |

**台ごとに違うもの**

- **`.ics` のキャッシュ**はプロセス内（`CALENDARFEED_FEED_CACHESECONDS`。既定 300 秒）。台によって、古さが最大でこの秒数ずれる
- **購読 URL のレート制限**（IP ごと 1 分に 60 回）は、要求が多く DB への書き込みが重いので、台ごとの数え。台数ぶんだけ通る
- 定期処理（古い監査ログ・期限切れのセッション・レート制限の古い行の掃除、設定の読み直し）は、**全台で走る**。消す処理は同じものを二度消しても害がない

**SQLite は複数台に向かない**（1 つのファイルを複数のホストで共有しない前提。同じホストの複数プロセスなら動くが、ロックの競合が増える）。複数台は SQL Server・PostgreSQL・MySQL で。

## 8. 困ったとき

### 8.1 秘密の鍵を失った・変えた

`CALENDARFEED_SECRET_KEY` を失う、または変えると、DB に保管した**暗号文を復号できない**。

| 影響 | 症状 | 対処 |
| --- | --- | --- |
| フィードごとの API キー | 購読 URL が **502**（ログに `フィード … の API キーを復号できません`） | **API キーを登録し直す**（`PUT /admin/api/feeds/{id}/apikey`）。Pleasanter 側のキーはそのまま使える |
| 管理者の TOTP の共有鍵 | TOTP のログインが通常の失敗（401）になり、ログに `TOTP の共有鍵を復号できません` | **復旧コードで入る**（復旧コードは鍵に依存しない。テストで確認）。入ったら **2 要素を登録し直す**（4.5。古い共有鍵は上書きされる） |

- **鍵の保管が最大の予防。** コンテナ・ディスクが作り直されても残る保管先（アプリケーション設定・Key Vault の参照など）へ置く。
- **鍵のローテーション（再暗号化）は未対応。** 鍵を変える＝全フィードの API キーの登録し直し。
- 復旧コードも失くした場合は 8.2 の DB 操作しかない。

### 8.2 管理者のパスワードを忘れた・全員がログインできない

管理者のパスワードのリセットは、**招待の出し直し**で行う（`POST /admin/api/users/{id}/invitation`。受け取ると決め直しになり、以前のセッションは失効する）。**管理者が 1 人も入れなくなった場合の最後の手段は DB の操作**（**必ずバックアップを取ってから**）。

```sql
DELETE FROM "AdminRecoveryCodes";
DELETE FROM "AdminSessions";
DELETE FROM "AdminUsers";
DELETE FROM "AdminSetup";
```

- 識別子の引用符は RDBMS による（SQL Server は `[AdminUsers]`、MySQL は `` `AdminUsers` ``）。
- **フィードと API キーは消えない。** 消したあと、4.4 から最初の管理者を作り直す。
- 同じ 4 表を空にして最初の管理者を作り直せることは、4 種の RDBMS のテストで確認している。
- 管理者を作り直すまで、管理 API は 401 のまま（購読フィードは影響を受けない）。

### 8.3 応答の意味

| 応答 | 場所 | 意味と対処 |
| --- | --- | --- |
| 404 | 購読 URL | トークンが違う・フィードが失効した・トークンを再発行した。**どれも同じ 404**（有効なトークンを推測させない） |
| 502 | 購読 URL | API キーが未登録で共通の既定も無い／API キーが Pleasanter に拒否された（失効・権限）／API キーを復号できない（8.1）。ログに理由（フィード ID つき） |
| 503（`Retry-After: 60`） | 購読 URL | Pleasanter に接続できない・Pleasanter が一時的に不調 |
| 429 | 購読 URL・ログイン | レート制限。**プロキシ配下で転送ヘッダを信頼する設定が無いと、全員で共有**（7 章） |
| 304 | 購読 URL | 前回と同じ内容（`ETag`）。正常 |
| 401 | 管理 API | ログインしていない／セッションの期限切れ（8 時間）／2 要素の途中（Pending）で操作しようとした |
| 401 | ログイン | **理由は伝えない**: ID が無い・無効・締め出し中・パスワードが違う・数字が違う・同じ時間枠の数字（盗み見の再利用）。**5 回失敗で 15 分締め出す**（恒久的ではない） |
| 403 | 管理 API | 別のサイトからの要求（`Origin` / `Sec-Fetch-Site`）。ブラウザ経由でなければ出ない |
| 予定が出ない・時刻がずれる | `.ics` | 開始が未設定／文字の日付が書式に合わない（そのレコードだけ出ない）。時刻のずれは API キー利用者のタイムゾーンと設定の不一致（2 章） |

### 8.4 ログに出るもの

| ログ | 意味 |
| --- | --- |
| `設定ファイルの置き場 … 見つかったファイル …` | 設定の読み込み。**空なら置き場を確かめる** |
| `管理者 … を … まで締め出しました` | ログイン・数字の失敗が続いた |
| `管理者 … が復旧コードでログインしました` | 復旧コードの使用。**心当たりが無ければ調べる** |
| `フィード … の取得に失敗しました（…）` | Pleasanter の失敗（種類つき）。**API キー・トークンは出ない** |
