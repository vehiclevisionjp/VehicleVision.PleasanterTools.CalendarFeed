## 1. 日時は「API キー利用者のタイムゾーン」で返る（確定）

同じレコード（`StartTime` に `2026-03-01T09:00:00` を送って作成）を、利用者の `TimeZone` を変えて取得した。

| 利用者の `TimeZone` | `StartTime` | 備考 |
| --- | --- | --- |
| `UTC` | `2026-03-01T09:00:00Z` | **末尾に `Z` が付く** |
| `Tokyo Standard Time` | `2026-03-01T18:00:00` | `Z` は付かない |

- **`Z` は飾りで、時刻は利用者のタイムゾーンの壁時計**。`Z` やオフセットを見て動かさず、書かれている時刻をそのまま
  API キー利用者のタイムゾーンとして読む実装（`EventMapper`）は正しい
- 型付きの日付（`DateHash` の `DateA` など）は `Z` が付かない
- **DB には Pleasanter サーバの OS 時刻で書かれる**（`UpdatedTime` を `KeyValues` の `Value` で取ると `19:43:23` で、
  OS が `Asia/Tokyo` のため。`Text` / 既定では利用者の時刻 `10:43:23Z`）
- **日付だけを入力したレコードを、運用の標準タイムゾーンで 0:00 に読むには、API キーの利用者の `TimeZone` を
  そのタイムゾーン（日本なら `Tokyo Standard Time`）にしておく必要がある。**
  `UTC` の利用者で読むと、同じ「3/5」が `3/4 15:00` や `3/5 09:00` に見え、終日の自動判定（0:00 開始）が効かない
  - 利用者 `UTC` で `2026-03-05T00:00:00` を送って作ったレコードを `Tokyo Standard Time` の利用者で読むと `2026-03-05T09:00:00`
- **API キー利用者の `TimeZone` を変えると全予定の時刻がずれる**（Questionnaire の結果と同じ。1.5.8.1 でも確認）

→ `ApiKeyUserTimeZoneId` は、**API キーの利用者の `TimeZone` と一致させる**。運用手順書へ書く。

## 2. 未設定の日付

- `DateA` など**型付きの日付の未設定は `1899-12-30T00:00:00`**（Questionnaire の結果と同じ。1.5.8.1 でも確認）
- **期限付きテーブルの `StartTime` / `CompletionTime` は未設定にならない。** `StartTime` を送らずに作ると
  **作成した日の 0:00**、`CompletionTime` は**その 7 日後**が入る。「開始が無い予定は出さない」が効くのは `DateX` を開始にした場合だけ

## 3. `ItemTitle` が返り、選択肢の表示名に解決されている

`ClassA` の選択肢を `1,会議` / `2,出張`、サイトの `TitleColumns` を `["ClassA","Title"]`（`TitleSeparator` は半角空白）にしたとき

| `ClassA` | `Title` | `ItemTitle` |
| --- | --- | --- |
| `1` | 時間つき | `会議 時間つき` |
| `2` | 日付だけ | `出張 日付だけ` |
| （空） | 日付なし | `日付なし` |

- **`ItemTitle` は生の値（`1`）ではなく表示名（`会議`）に解決される。** 空の列は詰められる
- したがって件名の既定を `ItemTitle` にしたのは正しい（選択肢・リンクの解決を自前で持たずに済む）

## 4. 完了日（`CompletionTime`）の終了日は包含

`CompletionTime` の列の入力形式を日付のみ（`EditorFormat: Ymd`）にして、`2026-03-06T00:00:00` を送って作成したレコードを取得すると、
**`2026-03-06T00:00:00` が返る**（送った値と同じ。内部では +1 日で保存されるが、API は表示値を返す）。
→ 終日の終了日は包含で、`DTEND` を翌日にする変換が正しい。

## 5. `View.ApiDataType = KeyValues` は日時には使えない（Issue #5）

`GridColumns` に指定した列だけがフラットな JSON で返る。`ApiColumnValueDisplayType` ごとの結果:

| 種類 | 文字・選択肢（`ClassA`） | 日時（`StartTime` / `CompletionTime` / `DateA`） |
| --- | --- | --- |
| `Text`（2） | **`会議`（表示名に解決）** | **`03/01/2026`（ロケール依存・日付だけ。時刻が落ちる）** |
| `DisplayValue`（0） | `会議` | 列によって `03/01/2026`（日付だけ）か `2026-03-01T19:30:00`（時刻つき）。**揃わない** |
| `Value`（1） | `1`（生の値） | **DB の値**（サーバの OS 時刻のまま。`CompletionTime` は +1 日で保存された値） |

→ **日時は既定の `Get`（`ClassHash` / `DateHash` などのある形）から取り、表示テキストが要る文字の列だけ
`KeyValues` ＋ `Text` で別に取って、`IssueId` / `ResultId` で突き合わせる**のが現実的。
`Id` は `Text` でも文字列（`"4"`）で返る。件名だけなら `ItemTitle` で足りるので、この突き合わせは
「任意の列を組み合わせたタイトル」「場所・説明に選択肢やリンクの列を使う」ときだけ要る（Issue #5）。

## 8. 文字の列に入った日付を書式で読む（Issue #14。2026-10-12）

`DescriptionA` / `DescriptionB` に日付を文字で入れた 3 件（`2026/03/05`〜`2026/03/06` / `2026/03/10 14:00`〜`15:30` / `未定`）を、

| 確かめたこと | 結果 |
| --- | --- |
| ログイン開始 → IdP → ACS → 管理画面 | 通った。**ログインの途中の cookie は `SameSite=None; Secure`** なので、**本アプリも HTTPS で立てる**（HTTP では戻りで cookie が付かない） |
| SP 起点の単一ログアウト | 本アプリのセッションを捨て、IdP の単一ログアウトへ進む。戻った後は 401 |
| 本アプリに居ない人（`Reject`） | `?samlError=unknown-user` で画面へ戻す |
| 自動登録（`Register`・役割 `Auditor`） | 利用者が作られ、その役割で入れた |

- ⚠️ **ITfoxtec.Identity.Saml2 4.21.0 は、応答の `Destination` を確かめない。** 別のサービス宛ての応答（宛先が異なる）でセッションが作れることを**テストで確認した**ので、
  ACS の URL との照合を本アプリで足した（`destination-mismatch`）
- IdP 起点の単一ログアウトは、**他サイトからの POST で cookie が届かない**ので、cookie ではなく NameID・SessionIndex でセッションを探して失効させる。
  署名のない要求は受け付けない（Keycloak 側の実機では、IdP 起点の単一ログアウトまでは通していない。**単体テスト（`FakeIdp`）で確認**）
- こちらからの要求（AuthnRequest・ログアウト要求）には**署名を付けない**。署名を求める IdP とは繋げない（検証用の Keycloak は求めていない）

## 11. 検証用の Pleasanter の起動は、ポートが開いてからも待つ（2026-10-15）

**Pleasanter 1.5.8.1 は、起動（再起動を含む）の最後に暖機（`Application Warmup`）がある。** コンテナの `healthcheck`（TCP の待ち受け）が通っても、
**API は暖機が終わるまで 503 を返す**（CI で踏んだ）。検証・試験は、**ログイン画面（`/users/login`）が 200 を返すまで**待ってから始める
（`.github/workflows/e2e.yml`。実行の遅い環境でも足りるよう 5 分）。

- **再起動の後に `docker compose up --wait` をやり直さない。** CodeDefiner が走り直し、起動中の Pleasanter の DB 接続を巻き込んで、3 分待っても応答しなかった
- 利用者の情報はキャッシュされるので、`Users` を直接書き換えたら、Pleasanter を再起動して捨てる

## 12. 日付の範囲の絞り込み（`View.ColumnFilterHash`）。フィードに出す期間に使う（Issue #67。2026-10-15）

**Pleasanter 1.5.8.1 の実機**で、`tools/pleasanter-testenv/verify/range.py` を通した（応答は `results/range_*.json`）。ソースでも確かめた
（`Libraries/Settings/View.cs` の `CsDateTimeColumns`）。

- **値の書式は、JSON の配列を文字列にしたもの `["from,to"]`。** **`from` か `to` を空にすると開区間**（空の `to` は `>=`、空の `from` は `<=`）。
  日時は `2026/03/01 00:00:00`（秒まで）・`2026-03-01T00:00:00` のどちらも読める。**`to` に日付だけ（`2026/03/31`）を書くと、その日の 0 時まで**になり、その日の予定が漏れる（時刻まで書くこと）
- **範囲は両端を含む**（`between`）。**終了が窓の始まりちょうどの予定も、開始が窓の終わりちょうどの予定も返る**ので、正確な判定は取得した後に本アプリで行う
- **列ごとの絞り込みは AND。** 開始の列に「`,窓の終わり`」、終了の列に「`窓の始まり,`」を同時に付けると、**期間と重なる予定**（開始 ≦ 窓の終わり かつ 終了 ≧ 窓の始まり）が返る。
  長い予定（窓を丸ごと含む・窓の前に始まって今も続く）も返る
- **日付の列（`DateA` など）にも同じ書式で効く。**
- **比べる時刻は、予定の時刻と同じ壁時計**（`range.py` で、秒単位の境界（`23:59:59` に始まる予定・`00:00:00` に終わる予定）が、そのとおりに効いた）。**`ApiKeyUserTimeZoneId` を API キー利用者のタイムゾーンに合わせる前提は変わらない**（1 章）
- **日付が文字の列（`Class*` など）には使えない**（文字として比べる）。その場合は取得した後の判定だけが効く
- **未確認:** 絞り込みの値に `Today`・`ThisMonth`・`ThisYear` などの語がある（ソースにある）が、本アプリは使っていない。**タイムゾーンの異なる利用者（`UTC` と `Tokyo Standard Time`）で、境界がずれないかは、確かめていない**

本アプリへの通し（期間つきのフィードを作って `.ics` を取る）も、同じ実機で確かめた: 過去 200 日（2026-03-29 から）・未来無制限で、窓の前に終わる予定（4 件）が消え、窓をまたぐ長い予定は残った。
両側を無制限にすると 8 件すべて、未来 0 日（今日の終わりまで）でも、すべて過去の予定なので 8 件が出た。

## 13. API の回数制限（`Api.json` の `LimitPerSite`）に当たったとき（Issue #69。2026-10-15）

**Pleasanter 1.5.8.1 の実機**で、`LimitPerSite` を 5 にして（`tools/pleasanter-testenv/docker-compose.limit.yml`）、`verify/limit.py` で確かめた。
ソース（`Models/Sites/SiteModel.cs` の `WithinApiLimits`）とも照らした。Questionnaire の確認とは別に、CalendarFeed の取得（`Get`）で確かめた。

| 確かめたこと | 結果 |
| --- | --- |
| 数え方 | **サイトごと・1 日ごと。** 1 回の `Get` ＝ 1 回。**作成（`Create`）も同じサイトの回数に入る**（上限に達した後の `Create` も 429） |
| 上限までの応答 | 成功の応答に `LimitPerDate`（上限）と `LimitRemaining`（残り）が入る（5 → 4 → … → 1 と減った）。**上限が 0（無制限）のときは `null`** |
| 超えたとき | **HTTP 429、本文の `StatusCode` も 429。** メッセージは「ID {サイト ID} のサイトで使える API の上限（{N} 回/日）を超えました」。`LimitPerDate`・`LimitRemaining` は `null` |
| 超えた後 | 以降も 429 が続く（実機）。超えた呼び出しは数えに加わらない（ソース） |
| 日の区切り | **API キーの利用者のタイムゾーンの日付が変わると 0 に戻る**（ソース。`DateTime.Now` を利用者のタイムゾーンへ直した日付で比べる）。**実機では、日付をまたぐ確認はしていない** |
| `Api.json` の既定 | `LimitPerSite: 0`（無制限）。**契約の設定（`ApiLimitPerSite`）があればそちらが優先**（ソース。実機では未確認） |
| MCP | 数えの対象外（ソース） |

**本アプリの挙動**（上限に達したサイトで、購読 URL を取得して確認した）:

- **修正後（Issue #71）:** 429 は専用の失敗（`RateLimited`）。購読 URL は `503`＋`Retry-After`（**API キー利用者のタイムゾーンで次の 0 時＋1 分まで**。最短 60 秒・最長 24 時間）。管理画面の取得結果と失敗の通知のメールに「上限に達した」と対処（上限を上げる・キャッシュ秒数を伸ばす）を出す

**修正前の挙動**（参考。Issue #69 の確認時）:

- **Pleasanter の 429 は「一時的な失敗」（`Transient`）として扱われ、購読 URL は `503`＋`Retry-After: 60` を返す。** 管理画面の「最後の取得結果」には「Pleasanter が HTTP 429 を返しました。」と出て、連続の失敗として数えられ、失敗の通知（Issue #48）の対象になる
- **上限は日付が変わるまで戻らない**ので、`Retry-After: 60` は実態に合わない。クライアントは 1 分ごとに取り直す（Pleasanter は 429 を即座に返すので負荷は小さいが、無駄）
- 購読側のカレンダーは、503 のとき手元の予定をそのまま残す（Outlook・Google・Apple での確認はしていない）

**使う回数の見積もり**（取得の仕組みから）: 1 回の更新（キャッシュが切れたとき）で、ページごとに `Get` を 1 回（表示名の解決が要る列があるときは、もう 1 回）呼ぶ。
キャッシュ（既定 300 秒）が効くので、**購読者が絶えず取りに来る場合の 1 日の上限は、1 フィードあたり `86400 ÷ キャッシュ秒数 × 1〜2 回`（既定で最大 288〜576 回/日）**。
**同じサイトを使う複数のフィードの分は足される**（上限はサイトごと）。Pleasanter 側の上限がこれより小さいと、日中に使い切る。

## 14. CalDAV 書き込みの前提: 更新の競合・削除（Issue #85。2026-10-16）

**Pleasanter 1.5.8.1**（検証環境）。スクリプトは `tools/pleasanter-testenv/verify/caldav_write.py`。
更新と削除は標準 API（`api/items/{id}/update`・`delete`）で確かめた。

| 確かめたこと | 結果 |
| --- | --- |
| 取得（`get`）の応答に `Timestamp` が出るか | **出ない。** `UpdatedTime`（`2026-10-16T05:40:19Z`。**秒単位**。`Z` は飾りで実際は API キー利用者の現地時刻。メモリの確認どおり）と `Ver` だけ |
| 更新の本文へ `Timestamp` を載せる | **無視される。** 正しい値でも通り、古い値でも通る |
| **古い `Timestamp` で更新** | **HTTP 200 で通り、上書きされた**（題名が書き換わった）。競合の検出は **API では起きない** |
| `Timestamp` なしの更新 | 200 で通る（後勝ち） |
| `Ver` の動き | 連続する 3 回の更新の後も `Ver` は 1 のまま。更新の見分けには使えない |
| 削除（`delete`） | 200。以降の `get` は 404 |
| **削除後のデータ** | `Issues_deleted` に 1 行残り、`Issues`・`Items` からは消える。**ごみ箱へ移る**（ごみ箱からの復元は Pleasanter の画面） |

**ソースとの食い違い。** `Models/Issues/IssueModel.cs`（2146–2151 行）の更新は、`Timestamp` が範囲内なら `UpdatedTime` を条件に加え、

API の本文からは設定されない**ため、API の更新ではこの検査が働かない。
**設計への影響:** 競合の検出は本アプリで行う（`CalDAV書き込み-設計方針.md` 6 章）。

**未確認:** 上記は `Issues` テーブルの 1 サイトでの確認。日付をまたぐ・複数人の同時更新・`Results` テーブル（結果型のサイト）では未確認。
